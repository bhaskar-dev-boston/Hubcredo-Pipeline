# HubCredo

A guided sales infrastructure platform for founders — analyses your website, extracts your ICP, generates qualified LinkedIn leads, and recommends a personalised GTM stack.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 8080)
- `pnpm --filter @workspace/hubcredo run dev` — run the frontend (port 19953, via workflow)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- Frontend: React + Vite, Tailwind CSS v4, shadcn/ui, wouter (routing), TanStack Query
- API: Express 5 at `/api`
- DB: Supabase (external, tables already exist) via `@supabase/supabase-js`
- Validation: Zod (`zod/v4`)
- API codegen: Orval (from OpenAPI spec in `lib/api-spec/openapi.yaml`)
- Build: esbuild (CJS bundle)

## Where things live

- `lib/api-spec/openapi.yaml` — source of truth for all API contracts
- `lib/api-client-react/src/generated/` — generated hooks + Zod schemas (run codegen to refresh)
- `artifacts/api-server/src/routes/` — all Express route handlers
- `artifacts/api-server/src/lib/` — supabase client, auth middleware, stack logic
- `artifacts/hubcredo/src/pages/` — Landing, Login, Signup, Onboarding, Dashboard, Leads, Stack, Settings
- `artifacts/hubcredo/src/components/layout/` — Sidebar, DashboardLayout
- `artifacts/hubcredo/src/lib/auth.ts` — token helpers (getToken, setToken, removeToken)

## Architecture decisions

- Auth tokens stored in localStorage as `hubcredo_token`; injected into every API call via `setAuthTokenGetter` in `lib/api-client-react/src/custom-fetch.ts`
- Supabase is used server-side (service role) for all data access; client-side Supabase is lazy-loaded only for Google OAuth
- All mutations use `{ data: ... }` wrapper pattern (Orval codegen convention)
- n8n webhook URLs are server-side only — never exposed to the client
- `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` must be set as env vars (not secrets) for Google OAuth to work on the frontend

## Product

- **Landing** — marketing page with hero + features
- **Auth** — email/password sign up/in + Google OAuth
- **Onboarding** — 4-step wizard: company details → ICP job titles → target companies → done
- **Dashboard** — stats, analysis status, stack preview, quick actions
- **Leads** — create lead lists, trigger LinkedIn scraping via n8n, review/approve/reject leads
- **Stack** — view personalised tool recommendations or browse full catalogue
- **Settings** — update profile, ICP, and outreach settings

## User preferences

- Design: dark editorial — charcoal `#0E0E0E` bg, amber `#F5A623` accent, Bebas Neue display font, DM Sans body

## Gotchas

- All API mutations generated by Orval take `{ data: <InputType> }` as the argument, not the input object directly
- `StackInput` requires both `icp_id` and `settings_id` — can only build stack after ICP and outreach settings exist
- `LeadListInput` requires `icp_id` — can only create a list after ICP is configured
- `TriggerLeadScrapingInput` requires `user_id`, `icp_id`, `lead_list_id`
- The Supabase client on the frontend is lazy (`getSupabase()`) and throws if VITE env vars aren't set — Google OAuth will fail gracefully
- Run `pnpm --filter @workspace/api-spec run codegen` after any OpenAPI spec change before touching frontend/backend
